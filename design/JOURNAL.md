# Design Journal — issue-138-terran-zerg-mechanics

### 2026-05-30 · §Component Structure

`EmulatedGame` was Protoss-hardcoded in three places: `reset()`, `countProbesPerBase()`, and `tick()` income. Rather than adding inline switch branches per race (which would have grown the already-large class and tangled race mechanics with physics), all race-specific behaviour was extracted behind a `RaceModel` interface in `sc2/emulated/`. The three SC2 implementations (`ProtossRaceModel`, `TerranRaceModel`, `ZergRaceModel`) live alongside the interface; `EmulatedGame` holds a `RaceModel playerRaceModel` field (default `ProtossRaceModel`) and delegates seeding, passive ticking, production resource checks, and unit spawn callbacks. `ProductionResult` (PROCEED/HANDLED/BLOCKED) replaces a confusing boolean return that inverted meaning. `RaceModelFactory` maps `Race → RaceModel`. The `countProbesPerBase` static method was renamed to `countWorkersPerBase` with a `RaceModel` parameter; the public `Race`-overload caches static model instances to avoid per-call allocation. `SC2Data` gained Terran/Zerg unit stat entries (train times, supply, mineral/gas costs, max HP, combat stats) and three new constants: `MULE_LIFETIME_LOOPS`, `QUEEN_ENERGY_REGEN_PER_LOOP`, `muleIncomePerTick()`. `trainCount(UnitType)` was added to `SC2Data` as a data fact (ZERGLING→2, others→1) but is also overridable on `RaceModel.trainCount()` so future non-SC2 race plugins aren't constrained by the static class.

### 2026-05-30 · §Core Agent Loop Decisions

The `RaceModel` interface is a forward-looking plugin seam for issue #74 (pluggable races: SC2 as a plugin, not baked-in). Choosing a plugin seam over inline conditionals was deliberate: inline conditionals would tangle Zerg larva regen, MULE expiry, and Queen energy logic with movement and combat code that has no race dependency. With `RaceModel`, each race is independently readable and testable. The `canProduce`/`onProductionCommitted` split was required because an earlier single-method design (with a boolean return) consumed Zerg larva before the resource check, leaving a stranded EGG if minerals were insufficient. The two-phase approach (`canProduce` — read-only check, `onProductionCommitted` — mutate after resources confirmed) eliminates that ordering hazard. `TerranRaceModel.canProduce` is an exception: it mutates state when returning `HANDLED` (spawns the MULE unit immediately), which is documented in the interface contract. The `RaceModel` interface lives in `sc2/emulated/` alongside the package-private `PlayerState`; when #74 lands and race plugins become external, `PlayerState` will need a public mutator surface (tracked as #164).

### 2026-05-30 · §Testing Strategy

Two new plain-JUnit (no `@QuarkusTest`) test classes: `TerranEmulatedGameTest` (11 tests: initial state, SCV/Marine/Marauder/MULE training, MULE expiry, OC as town hall) and `ZergEmulatedGameTest` (19 tests: initial state, Drone income, larva regen and cap, Zergling/Roach/Overlord/Queen training, EGG lifecycle, Queen energy and auto-inject, inject larva cap, town hall assignment, multiple hatcheries, reset clears race model state). `SC2DataTest` gained 40 new tests covering all added Terran/Zerg entries and the three new constants. `EmulatedGameTest` (102 tests, unchanged pass count) is the primary regression guard: the `ProtossRaceModel` default means all existing Protoss tests run without modification.
