Fog of War — Architecture Approaches

Where does visibility computation live?

A

VisibilityGrid inside EmulatedGame (recommended)

EmulatedGame owns a VisibilityGrid (64×64 tile states: UNSEEN / MEMORY / VISIBLE). It recomputes the grid each tick from friendly unit positions + terrain heights. observe() filters enemyUnits before returning. A new observeVisibility() method exposes the grid for broadcast.

Pros

  • All data in one place — terrain + units + visibility
  • MEMORY state naturally persists across ticks
  • Enemy filter is authoritative (same place enemies are created)

Cons

  • EmulatedGame grows slightly larger
  • Tight coupling between physics and perception
B

Visibility computed in EmulatedEngine

EmulatedGame stays pure physics. EmulatedEngine (the CDI layer above) reads GameState + TerrainGrid, computes visibility as a post-processing step, filters enemies, and attaches the grid to the broadcast.

Pros

  • EmulatedGame stays focused on physics
  • Visibility is an observation concern, not game state

Cons

  • Engine needs terrain access (currently in EmulatedGame)
  • MEMORY state must live outside the game — separate field in engine
  • More wiring

Data flow (either approach)

EmulatedGame.tick() → compute VisibilityGrid from units + terrain
EmulatedGame.observe() → return GameState with filtered enemyUnits
GameStateBroadcaster → WebSocket: { gameState, visibility: int[64][64] }
Visualizer → fog layer updated each tick (0=black, 1=grey, 2=clear)

What changes across the codebase

New
  • VisibilityGrid — 64×64 tile states + compute logic
  • SC2Data sight ranges (per unit + building type)
  • Visualizer fog overlay layer
Modified
  • EmulatedGame — owns/computes visibility, filters observe()
  • GameStateBroadcaster — adds visibility to WebSocket payload
  • visualizer.html — fog layer, 3-state rendering
